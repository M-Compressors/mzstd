# lzbench run, 2026-11-24

The zstd 1.6.0 update (see the [changelog](../../CHANGELOG.md)) against the
tree it was made on, measured with the lzbench in-memory benchmark on the
Silesia corpus. **Before** is commit `813caf0` (0.2.15 plus the `hotpath`
bump) with zstd 1.5.7; **after** is the working tree with the 1.6.0
changes, with zstd 1.6.0. Each lzbench binary holds one zstd and one mzstd,
so mzstd is compared with the reference it is byte-identical to.

## Environment

- lzbench master at
  [`3d95d12`](https://github.com/inikep/lzbench/tree/3d95d124c2d31def214796cf93fc92ee27775ca4)
  (2026-11-23, lzbench 2.4.2), built twice with `BUILD_ONLY='ZSTD MZSTD'
  MOREFLAGS="-march=native"`: once with its vendored zstd replaced by the
  1.5.7 sources of this repository's submodule (byte-identical to what
  lzbench vendors), once by the 1.6.0 sources. mzstd is linked as the
  `mzstd-ffi` static library built with `RUSTFLAGS="-C target-cpu=native"`
  and called through `mzstd_compress`/`mzstd_decompress`, so both sides
  target the same CPU. lzbench calls zstd with `ZSTD_compress2` and
  `ZSTD_decompressDCtx` on reused contexts, and mzstd's one-shot C calls
  allocate per call, which counts against mzstd at every level alike.
- gcc 11.4.0, rustc 1.100.0.
- Intel Core i7-13700KF under WSL2 (Linux 6.18), pinned with
  `taskset -c 4`; the machine ran nothing else.
- Input: `silesia.tar`, 211,947,520 bytes (the twelve Silesia files as
  lzbench publishes them), compressed as one stream.

## Command

Each level and codec ran as its own process, interleaved level by level
(zstd, then mzstd), as

```sh
taskset -c 4 ./lzbench -t8,8 -i1,1 -p1 -o4 -e<codec>,<level> silesia.tar
```

Rounds 1 and 2 covered every level, alternating the before and after
binaries (before, after, before, after). Rounds 3 to 5 repeated levels -5,
-1, 15 and 18, whose first two rounds differed the most. Every
decompression was verified by lzbench (`memcmp`), with no error.

Median ratio over the twelve levels: compression 0.998,
decompression 0.994.

The decoder's source did not change, yet its fastest decompression moved by
up to 10% between the two binaries (level 18). Between rounds of one binary,
a level's speed varied by a median of 2-5% and by up to 15%. At levels 15 to
22 lzbench measures one compression of the 212 MB input per run (a level 18
compression takes about 35 seconds), and level 18's before figure is one
round at 6.9 MB/s against 5.9 MB/s in the other four; after was 5.6-5.9 MB/s
in all five. Level -1 compressed at 692-742 MB/s before and 676-728 MB/s
after.

## Conclusion

No regression is attributable to the change. The encoder paths it touches
(the LDM gear reset and hash log, the split budget, dictionary entropy
loading and `freq_from_bit_cost`) run on this input only at level 22 (LDM)
and in the splitter of levels 16 and up, and every difference measured is
within the run-to-run spread of an unchanged decoder. zstd 1.6.0 itself is
within the same noise of 1.5.7 on x86-64, as its release notes, whose
speedups target AArch64 and RISC-V, suggest.
